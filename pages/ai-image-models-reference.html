AI Image Models: Reference

Pipeline components, model landscape, quantisation formats, architecture types, ComfyUI folder placement, and prompt dialect — one reference for the full stack.

Every image generation workflow in ComfyUI is a graph of connected nodes. Understanding what each component does — and why it is a separate file — removes the confusion about why modern models require three or four separate downloads instead of one. The signal chain is invariant: prompt feeds a text encoder, which produces a conditioning embedding; the KSampler runs that embedding plus random noise through the diffusion model for N steps guided by the scheduler; the clean latent exits and passes through the VAE decoder to become a pixel image. Each link in that chain is a distinct neural network with its own file, format, and compatibility constraints — and mixing components across model families breaks assumptions baked into the weights.

0. Core Pipeline Components

The six nodes every workflow contains, what they do, and the most common mistakes at each stage.

Signal chain: text → Text Encoder → conditioning embedding → KSampler feeds this plus random noise into the Diffusion Model (N times per the Scheduler) → clean latent → VAE Decode → pixel image.

Text Encoder —(CLIP / T5 / LLM)

Converts your text prompt into a numerical representation (embedding) the model can work with.

How it worksOlder models (SDXL) use CLIP — short prompts, keyword-based. Modern models use T5-XXL or full LLMs (Mistral-3, Qwen3). LLM encoders understand grammar, relationships, and long complex sentences far better.
Files by modelSDXL: CLIP-L + CLIP-G  ·  Flux.1: CLIP-L + T5-XXL  ·  Flux.2: Mistral-3 24B  ·  Z-Image: Qwen3-4B  ·  Qwen-Image: Qwen-VL
Common mistakeLoading the wrong encoder for your model. T5 is the reason Flux handles long descriptive prompts much better than SDXL. Loads separately via DualCLIPLoader / CLIPLoader.

Diffusion Model —(UNet / DiT)

The core image generation engine — takes the text embedding plus a noisy latent and iteratively removes noise to produce your image.

How it worksThe main model file (12B or 20B parameters). Does NOT work on pixels — it works entirely in compressed latent space. Does not understand text itself; the text encoder hands it a pre-digested embedding.
ArchitectureSDXL: UNet  ·  Flux / SD3 / Qwen / Z-Image: DiT. Architecture determines everything downstream — scheduler choice, LoRA compatibility, VAE pairing.
ComfyUI node"Load Checkpoint" for SDXL (all-in-one). "Load Diffusion Model" for Flux, Qwen, Z-Image (diffusion model only — encoders and VAE are separate files).

VAE —(Variational Autoencoder)

Compresses full-resolution images into a smaller latent representation for the diffusion model to work in — and decompresses them back to pixels at the end.

How it worksWithout a VAE, the diffusion model would need to work at full pixel resolution, which is prohibitively expensive. The VAE is a lossy compressor: it trades some information for massive speed and memory savings. VAE quality directly affects colour accuracy, sharpness, and fine detail.
Files by modelFlux.1: ae.safetensors  ·  Flux.2: flux2-vae.safetensors  ·  SDXL: sdxl-vae-fp16-fix.safetensors  ·  Qwen-Image: its own separate VAE
Critical ruleVAEs are NOT interchangeable between model families. Modern models (Flux.2, Z-Image) use a 16-channel VAE vs the 4-channel VAE of SDXL — swapping them produces washed-out or distorted images immediately. Place all VAE files in models/vae/.

Scheduler —(Sampler Schedule)

Controls how noise is added and removed across the diffusion steps — the mathematical trajectory from pure noise to clean image. Not a neural network; it's an algorithm.

How it worksDifferent schedulers produce different results at the same step count. Flow Matching models (Flux) use straight-line probability-space trajectories — fundamentally different math from DDPM. This is why DDPM schedulers (DPM++, Karras, DDIM) cannot be freely swapped onto Flux.
Common schedulersDPM++ 2M Karras (SDXL quality, ~20 steps)  ·  Euler / Euler a (SDXL fast)  ·  Simple / SGM Uniform (Flux)  ·  DPM++ 3S (Qwen-Image fast, ~10 steps)
Common mistakeUsing DPM++ Karras or DDIM on a Flux model. Use Simple or SGM Uniform for Flux. Set inside the KSampler or SamplerCustomAdvanced node.

KSampler —(The Sampler Node)

The node that runs the denoising loop — calls the diffusion model N times, guided by the text embedding and scheduler, to produce the final clean latent.

How it worksAt each step, it asks the diffusion model "given this noisy latent and this prompt, what noise is here?" then uses the scheduler to take one denoising step. Also applies CFG: runs the model twice per step (conditioned + unconditional) and extrapolates toward the prompt. Flux models bake guidance in via distillation — CFG=1, one pass per step.
Key settingsSteps: 20–50 (standard), 4–8 (distilled)  ·  CFG Scale: 7–9 (SDXL), 1.0 (Flux schnell), 3.5 (Flux dev)  ·  Denoise: 1.0 = txt2img, <1.0 = img2img
NotesFor Flux, use the FluxGuidance node instead of standard CFG. SamplerCustomAdvanced gives more control than basic KSampler. Seed controls the initial noise pattern.

CLIP Text Encode —(Prompt Node)

Feeds your text prompt through the loaded text encoder and produces the conditioning embedding that guides the denoising process.

How it worksUsually two nodes — one for positive prompt (what you want) and one for negative prompt (what you don't). Flux models use no negative prompt: guidance is baked into the weights via distillation, so there is no unconditional pass for CFG to push against.
By modelSDXL: two CLIP Text Encode nodes (positive + negative)  ·  Flux.1/2: one CLIPTextEncodeFlux node with guidance parameter  ·  Qwen-Image: one text encode node, negative optional

VAE Decode —(Output Node)

Takes the final clean latent from the KSampler and runs it through the VAE decoder to convert it back into a full-resolution pixel image.

VariantsStandard VAE Decode for normal use. VAE Decode (Tiled) for very large images to avoid VRAM spikes during decoding. Latent upscale workflows: decode → upscale → re-encode → decode again.
Common mistakeIf output images look washed out, too saturated, or soft, the first thing to check is whether you loaded the correct VAE. The fp16-fix VAE for SDXL is critical — the original baked VAE in many SDXL checkpoints produces washed colours.

0b. What Each Component Actually Is

The "what it does" view tells you how to use it. This section explains what kind of mathematical object each component actually is — which makes the compatibility rules that follow make intuitive sense.

VAE —(Variational Autoencoder)

A neural network trained as a lossy compressor. Two halves: an Encoder (pixels → latent) and a Decoder (latent → pixels). "Variational" means it maps to a probability distribution in latent space, not a fixed point.

InternallyTrained separately from the diffusion model, then frozen. Compresses a 512×512 RGB image (786K values) into a small latent grid — e.g. 64×64×4 channels (16K values) for SDXL, or 128×128×16 for modern models. The diffusion model never sees pixels; it only manipulates these tiny latents. Because the VAE is lossy, reconstruction is not pixel-perfect — which is fine because the diffusion model fills in details from training anyway.
Key factsSDXL: 4-channel, 8× spatial compression  ·  Flux / Qwen / Z-Image: 16-channel, 8× spatial compression — richer encoding, better fine detail  ·  Files: ae.safetensors (Flux.1), flux2-vae.safetensors (Flux.2)

Text Encoder —(CLIP / T5 / LLM)

A neural network trained to map text into a high-dimensional vector space that the diffusion model can be conditioned on. The diffusion model learns to associate these vectors with visual concepts during training.

InternallyCLIP was trained by matching image-text pairs — it understands visual-semantic similarity but is limited in contextual reasoning. T5 is a sequence-to-sequence language model — it understands grammar, relationships, and negation much better. The encoder output is a tensor [batch, seq_len, hidden_dim] — each token becomes a vector. The diffusion model uses cross-attention at every layer to query this conditioning throughout the denoising process.
Key factsCLIP-L: 77-token limit, semantic matching  ·  CLIP-G (SDXL): larger CLIP, better style  ·  T5-XXL (Flux.1): 512-token limit, language understanding  ·  Mistral-3 24B (Flux.2): 32K-token limit, full LLM reasoning  ·  Qwen3-4B (Z-Image)  ·  Qwen-VL (Qwen-Image)

Scheduler —(Noise Schedule)

A mathematical function that defines how much noise exists at each step of the diffusion process, and how to compute the update from one noisy state to the next. Not a neural network — it's an algorithm.

InternallyDuring training, a random noise level (timestep t) is sampled, noise is added to the image latent, and the model learns to predict what noise was added. During inference, you start at t=T (pure noise) and run backwards. DDPM uses a fixed Markov chain. DPM++ uses ODE solvers to take larger, more accurate steps. Karras uses non-linear noise spacing that concentrates steps where they matter most. Flow Matching (Flux) uses straight-line trajectories in probability space — which is why DDPM schedulers don't work on Flux.
Key factsDDPM / DDIM: original formulation, 50–1000 steps  ·  DPM++ 2M Karras: best quality/speed for SDXL, ~20 steps  ·  Euler / Euler a: fast SDXL iteration  ·  Simple / SGM Uniform: Flow Matching (Flux)  ·  DPM++ 3S: fast option for Qwen-Image (~10 steps)

KSampler —(Denoising Loop)

Not a model — it's the inference loop that calls the diffusion model N times. At each step it asks: "given this noisy latent and this prompt, what noise is here?" then uses the scheduler to take one denoising step.

InternallyEssentially: for t in reversed(timesteps): noise_pred = diffusion_model(latent_t, t, conditioning); latent_{t-1} = scheduler.step(noise_pred, latent_t, t). Also applies Classifier-Free Guidance (CFG): runs the model twice per step (conditioned + unconditional) and extrapolates toward the prompt. CFG=7 means "move 7 steps in the direction of the prompt". Flux bakes guidance in via distillation — CFG=1, one pass per step, twice as fast.
Key factsSteps: 20–50 standard, 4–8 for distilled  ·  CFG Scale: 7–9 (SDXL), 1.0 (Flux), 3.5 (Flux dev)  ·  Denoise: 1.0 = txt2img, <1.0 = img2img  ·  Seed: controls initial noise pattern

LoRA —(Low-Rank Adaptation)

A fine-tuning technique that adds small trainable matrices alongside the frozen weights of a pre-trained model. At inference, the LoRA weights are merged with the base model at load time. Not a separate network — it modifies the existing one.

InternallyInstead of fine-tuning all N billion parameters, LoRA decomposes the weight update into two small matrices: ΔW = A × B, where A and B have rank r (typically 4–64). A 12B parameter model can be personalised with only 10–200 MB of adapter weights. Multiple LoRAs can be stacked. LoRAs trained on Flux.1 dev will NOT work on SDXL — they encode weight offsets for a specific architecture.
Key factsFile size: 10 MB – 300 MB  ·  Rank: 4 (minimal), 16–64 (typical), 128+ (high capacity)  ·  Scale: 0.5–1.0 safe, >1.5 risks artefacts  ·  Must match base model architecture exactly

Conditioning —(Embeddings)

The output of the text encoder — the numerical representation of your prompt that guides the denoising process. A tensor of floating-point vectors, one per token, passed into the diffusion model via cross-attention at every layer.

InternallyTensor shape: [1, seq_len, hidden_dim] — e.g. [1, 77, 768] for CLIP-L or [1, 512, 4096] for T5-XXL. Every transformer layer in the diffusion model has cross-attention heads that query this conditioning, asking "how relevant is each token to this patch of the image right now?" This is why longer structured prompts work better with T5/LLM encoders.
Key factsPositive conditioning: what you want  ·  Negative conditioning: what you don't want (not used in Flux — no unconditional pass)  ·  Empty conditioning: unconditional baseline for CFG  ·  Strength controlled by CFG scale

0c. Compatibility Rules & Resolution Constraints

The most common sources of errors and degraded output. The core rule: every component was co-trained or matched — mixing components across model families breaks assumptions baked into the weights.

Component Compatibility

VAE ↔ Diffusion Model

Why it mattersVAEs are NOT interchangeable between model families. Each model is trained end-to-end with a specific VAE, and the latent space encoding is baked into the diffusion model weights.
What breaksUsing the wrong VAE produces immediately visible problems: washed-out or oversaturated colours, loss of fine detail, blurry or distorted images. The 4-channel SDXL VAE and the 16-channel Flux VAE encode information completely differently — swapping them is like using the wrong codec to decode a video file. Even within SDXL, the original baked-in VAE has known FP16 precision issues — the fp16-fix VAE is the standard replacement. Flux.2 uses a different VAE than Flux.1.
Correct pairingsFlux.1: ae.safetensors  ·  Flux.2: flux2-vae.safetensors  ·  SDXL: sdxl-vae-fp16-fix.safetensors  ·  Qwen-Image: its own dedicated VAE  ·  Z-Image: Wan2.1 VAE (same team)

Text Encoder ↔ Diffusion Model

Why it mattersText encoders are architecture-specific. The diffusion model was trained to interpret conditioning from a specific encoder — feeding it vectors from a different encoder produces garbage or an immediate crash.
What breaksFlux.1 dev expects T5-XXL conditioning at 4096 dims. An SDXL CLIP encoder outputs 768 dims — the dimensions won't even match, causing an immediate crash. For Flux.1 you need BOTH CLIP-L and T5-XXL simultaneously via DualCLIPLoader. Flux.2 requires Mistral-3 — nothing else.
Correct pairingsFlux.1 [dev/schnell/kontext]: CLIP-L + T5-XXL (both required)  ·  Flux.2 [dev/klein]: Mistral-3 Small (24B)  ·  Z-Image: Qwen3-4B  ·  Qwen-Image-2512: Qwen2.5-VL-7B  ·  SDXL: CLIP-L + CLIP-G (both via DualCLIPLoader)

Scheduler ↔ Model

Why it mattersSchedulers must match the mathematical framework the model was trained with. DDPM-family schedulers (DPM++, Euler, DDIM, Karras) are incompatible with Flow Matching models (Flux).
What breaksDDPM models are trained to predict noise at discrete timesteps (0–999). Flow Matching models (Flux) use straight-line probability flows — the timesteps mean something completely different. Running DPM++ Karras on Flux produces degraded, incorrect results. SD3 and Flux share the same Flow Matching framework, so their schedulers overlap.
Correct pairingsSDXL: Euler a, DPM++ 2M Karras, DPM++ 3M SDE  ·  Flux.1 / Flux.2: Simple, SGM Uniform (not DPM++ / DDIM)  ·  SD3: same as Flux  ·  Qwen-Image: Euler + Simple (default), DPM++ 3S (faster)

LoRA ↔ Base Model

Why it mattersLoRAs encode weight offsets for a specific model architecture. A Flux.1 LoRA cannot be applied to SDXL, and vice versa. Even within Flux, a Flux.1 LoRA on Flux.2 is unreliable.
What breaksA LoRA file contains matrices shaped to match the exact weight dimensions of its target model. Applying a 12B Flux LoRA to a 3.5B SDXL model fails immediately — dimensions don't match. Multiple LoRAs stack fine within the same model but can conflict stylistically. Loading at strength >1.5 with any LoRA can produce artefacts.
Correct pairingsFlux.1 LoRA → Flux.1 only  ·  Flux.2 LoRA → Flux.2 only  ·  SDXL LoRA → SDXL only  ·  Strength: 0.5–1.0 safe, >1.5 risks artefacts  ·  No hard limit on simultaneous LoRAs but >3–4 often conflicts

Image Resolution Constraints

Resolution constraints come from how positional encoding is baked into model weights during training. Generating at the wrong size activates untrained positional combinations, producing artefacts, repeated subjects, or quality degradation.

Model Native / Optimal Resolution Multiple Requirement Resolution Behaviour Notes & Limits
SD 1.5 512 × 512 px Multiples of 64 Trained at 512px. Going above 768px causes repeating patterns (multiple subjects, tiled artefacts). Use Hi-Res Fix or tiled upscaling to go higher. Never generate above 768×768 directly. The UNet's positional encoding breaks at larger sizes. Use 512 → upscale → img2img workflow.
SDXL 1.0 1024 × 1024 px Multiples of 64 Trained at 1024px. Can go to ~1536px on long edge without major issues. Above that, repeating artefacts appear. Non-square aspect ratios work well (e.g. 1216×832). SDXL was the first model with native aspect ratio awareness. Common sizes: 1024×1024, 1216×832, 896×1152, 1344×768. Always multiples of 64 or generation fails.
Flux.1 dev / schnell ~1024 × 1024 px Multiples of 16 Flexible resolution — can generate at various aspect ratios natively. Has been tested well beyond 1024px without artefacts. No hard ceiling in normal use. Much more flexible than SDXL. Community has generated quality images up to 2048px and beyond. Quality degrades gracefully rather than producing artefacts.
Flux.2 dev ~1024 × 1024 px Multiples of 16 Same flexibility as Flux.1. The Mistral-3 text encoder supports 32K-token prompts — resolution flexibility matched by improved compositional quality at large sizes. Supports rectangular shapes freely (width + height both multiples of 16). Pro Ultra mode via API reaches up to 4MP (~2048×2048).
Flux.1 Kontext ~1024 × 1024 px Multiples of 16 Editing model — resolution is typically matched to the input image being edited. Output resolution generally matches the input to preserve coherence. When editing, keep output resolution matching input. Resizing during an editing workflow degrades identity and composition preservation.
Z-Image Turbo ~1024 × 1024 px Multiples of 16 DiT architecture — flexible resolution. 16 GB VRAM comfortable at 1024px. Larger sizes possible but generation time increases. Qwen-Image-2512 ~1328 × 1328 px No strict constraint

These are the tested sizes from the official repo. Use the official aspect ratio sizes where possible — the model was trained on specific resolutions. Arbitrary sizes work but the listed sizes are optimal. Native 2K landscape (1664×928) is its strength.
The "multiples of 64" rule for SDXL/SD1.5 is hard — ComfyUI will round or error. The "multiples of 16" rule for DiT models (Flux, Qwen, Z-Image) is softer but still recommended. The 16-channel VAE in modern models provides better reconstruction at higher resolutions than the 4-channel SDXL VAE.

0d. Generation Modes

All generation modes share the same core pipeline. What changes is: (1) what the KSampler starts from (pure noise vs a partially-noised image latent), (2) whether a mask constrains where generation happens, and (3) what additional conditioning beyond text is injected. The denoise parameter is the single knob that controls how much of the input image survives.

Mode Reference

Text to Image (txt2img)

Generate an image from a text prompt alone. The KSampler starts from pure random noise (denoise = 1.0) and denoises it fully, guided only by the prompt conditioning.

How it worksThe latent is initialised with random Gaussian noise seeded by your seed value. The diffusion model runs the full N steps from t=T (maximum noise) down to t=0 (clean). Changing the seed changes which region of the model's learned distribution you sample from.
Key settingsDenoise = 1.0  ·  Steps: 20–50 standard, 4–8 distilled  ·  No negative prompt on Flux — guidance is baked in. SDXL benefits significantly from a standard negative prompt.

Image to Image (img2img)

Take an existing image as a starting point and regenerate it with modifications guided by a text prompt. The input image is VAE-encoded into a latent and partially noised instead of starting from pure noise.

How it worksThe input image is VAE-encoded to a clean latent. Noise is added up to timestep t = T × denoise (not the full T). At denoise=0.5, you add 50% of maximum noise — the model keeps roughly half the original structure. At denoise=0.9, almost everything is replaced. The prompt then steers what the model reconstructs.
Key settingsDenoise: 0.3–0.9 typical  ·  Low denoise preserves structure  ·  High denoise = more creative freedom  ·  See the Denoise Continuum table below for the full breakdown.

Inpainting

Regenerate only a selected region of an image while leaving the rest untouched. A mask defines which pixels are regenerated (white) and which are preserved (black).

How it worksThe image is VAE-encoded to a latent. The mask is downsampled to latent resolution (8× smaller). Only the masked latent region receives noise — the unmasked region is held fixed. The model must generate content coherent with the preserved surroundings. Flux.1 Fill is BFL's official dedicated inpainting model.
Common mistakeArtefacts at mask edges usually come from poor mask feathering or too small a context region. Make the mask slightly larger than the object to replace so the model has edge context.

Outpainting (Uncrop)

Extend an image beyond its original borders. The existing image is placed on a larger canvas and the empty border region is inpainted by the model.

How it worksMechanically identical to inpainting — the original image occupies part of the canvas and the empty region is the mask. The model must extend scene geometry, lighting, and style without any pixel information in the extension region. Flux.1 Fill and Kontext are significantly better at outpainting than base models because they were trained on this task.
TipsUse a prompt describing the full extended scene, not just the addition. Overlap the mask slightly into the original image (5–10%) to give the model context for blending.

Image Variation (Redux / Style Transfer)

Generate a new image that preserves the style or content of a reference image without directly copying it. Uses CLIP Vision or IP-Adapter to extract visual features from the reference.

How it worksThe reference is passed through a CLIP Vision encoder to extract semantic/stylistic feature vectors — not the VAE (which preserves pixel content). These vectors are injected as additional conditioning alongside the text prompt. The model generates from noise as in txt2img, with soft visual guidance from the reference. Flux.1 Redux uses this approach; IP-Adapter is the SDXL-era equivalent.
Key settingsDenoise = 1.0 (starts from noise)  ·  Reference strength 0.0–1.0  ·  Unlike img2img, does NOT preserve composition — extracts abstract visual qualities. Good for style consistency across a batch.

Multi-Image Input (Kontext / Reference)

Provide multiple reference images simultaneously — the model edits, combines, or uses them for consistency. Architecturally distinct from IP-Adapter: the model reads and reasons about image content, not just style vectors.

How it worksFlux.1 Kontext and Qwen-Image-Edit encode reference images as visual tokens and concatenate them with the text conditioning. The model attends to all of them in self-attention, understanding relationships between images ("keep this face", "use this background"). IP-Adapter extracts abstract features; Kontext directly processes image content.
Use casesCharacter consistency, product photography, style-locked image series. Models: Flux.1 Kontext, Qwen-Image-Edit (1–10 input images). Prompt must explicitly reference what to do with each image.

ControlNet (Guided Generation)

Condition generation on a structural guide image — depth map, edge map, pose skeleton, line art, etc. The output structure is locked to the guide regardless of prompt creativity.

How it worksControlNet adds extra input channels to specific layers of the diffusion model. The guide image is processed by a separate small encoder and injected as residual additions into the UNet/DiT during denoising. Multiple ControlNets can be stacked with individual strength weights. For Flux, XLabs provides adapters (Depth, Canny, etc.).
Key settingsStrength: 1.0 = strong structural adherence, 0.3–0.5 = loose guidance  ·  Guide types: Depth, Canny, Pose, Lineart, Normal, Scribble  ·  Stacking Depth + Pose gives full body and spatial control simultaneously.

Upscaling Workflows (Hi-Res Fix / Latent Upscale)

Generate at a lower resolution, upscale the result, then run img2img at partial denoise to add high-frequency detail at the larger size.

How it worksGenerating at 2048px directly is expensive and risks artefacts. Standard workflow: generate at 1024px → upscale to 2048px (bicubic, RealESRGAN, or latent upscale) → img2img at denoise 0.35–0.6. "Latent upscale" skips the VAE decode/encode cycle — the latent is upsampled directly, then denoised again. Faster and avoids VAE reconstruction artefacts.
Key settingsPass 1: denoise 1.0 at native resolution  ·  Pass 2: denoise 0.4–0.55 sweet spot  ·  >0.7 = model ignores upscale and regenerates freely  ·  <0.25 = no detail added  ·  Upscalers: RealESRGAN_x4plus.pth, 4x-UltraSharp.pth

The Denoise Continuum

Denoise (also called "denoising strength") controls what timestep the KSampler starts from — and therefore how much of the original image can survive. It is the single most important parameter to understand in img2img, inpainting, and upscaling workflows.

Denoise Value Perceived Effect What's Happening Technically When to Use It
0.0 No change No noise added to the input latent. The KSampler runs zero denoising steps. Output = input image passed through VAE encode → decode only. Effectively a VAE round-trip. Useful only for testing VAE quality. Not a useful generation mode.
0.1 – 0.2 Micro-refinement Extremely subtle texture and sharpness adjustments. Composition, colours, and content completely preserved. The model is only making small local corrections. Useful for slight texture improvements or reducing digital smoothness. Prompt has almost no effect at this range.
0.3 – 0.45 Stylistic adjustment Structure, composition, and most content preserved. Colours, texture, and surface qualities shift noticeably. Good for style transfers while keeping the layout. The sweet spot for Hi-Res Fix pass 2 (adding detail to an upscale without changing composition). Prompt starts to influence the aesthetic.
0.5 – 0.65 Moderate reimagining General composition preserved (rough positions of main subjects), but significant content changes are possible. Lighting, style, fine details all shift substantially. Good for img2img creative variations. The model "remembers" the layout but rewrites the details. Prompt has strong influence. Common for iterative refinement workflows.
0.7 – 0.8 Heavy reinterpretation Only the broadest structural suggestions from the input survive — rough brightness distribution, very general composition. Most content is regenerated from the prompt. Used when you want loose inspiration from a reference rather than preservation. The original image functions more as a composition hint than a content source.
0.9 – 0.95 Near-full regeneration Almost nothing from the original image is preserved. The faintest shadow of the original structure may subtly influence the output. Essentially txt2img with a weak initial bias. Rarely useful. At this range you may as well use txt2img with a more detailed prompt. The tiny residual influence is not predictable.
1.0 Full txt2img Pure random noise. No input image influence whatsoever. Complete creative freedom within the prompt. The input image (if any) is entirely ignored. Standard txt2img mode. The seed controls the initial noise pattern. Changing the seed while keeping the prompt gives a different image from the same distribution.
The same denoise value produces different levels of change depending on the model, scheduler, step count, and CFG scale. These ranges are guidelines for standard SDXL/Flux workflows at 20+ steps. Distilled models (Flux schnell, Z-Image Turbo) with 4–8 steps behave differently — a denoise of 0.5 at 4 steps is not equivalent to 0.5 at 30 steps.

0e. The Empty Latent Image Node

Every txt2img workflow in ComfyUI contains an Empty Latent Image node. It is often overlooked because it feels like a trivial "set the canvas size" step — but understanding what it actually creates explains why the diffusion pipeline is structured the way it is.

What the node does: it creates a blank tensor of zeros in latent space — not a pixel canvas. This tensor is the starting point the KSampler will immediately fill with random Gaussian noise (seeded by your seed value) before denoising begins. Without it, the KSampler has nothing to work with.

Why latent space, not pixels? The diffusion model never sees or generates pixels. It works entirely inside the compressed latent space produced by the VAE encoder. At the end of the pipeline the VAE decoder converts the final denoised latent back into a pixel image. The Empty Latent Image node creates the correctly-shaped container for this latent-space process.

Setting What It Controls Detail
Width Output image width in pixels The node divides by 8 internally (VAE compression factor) to compute latent width. 1024 px → 128 latent units. Must be a multiple of 64 (SDXL) or 16 (DiT models).
Height Output image height in pixels Same 8× compression applies. Non-matching multiples cause artefacts or ComfyUI rounding errors.
Batch Size Number of images generated in one pass Batch 4 = 4 independent latents denoised in parallel. Multiplies VRAM usage roughly linearly. Each image in the batch uses a seed offset (+0, +1, +2…).

The latent tensor shape created:

Model Family Channels Latent Shape (1024×1024 example)
SDXL / SD1.5 4-channel [batch, 4, 128, 128]
Flux.1, Flux.2, Z-Image, Qwen-Image 16-channel [batch, 16, 128, 128] — encodes richer information per spatial unit, contributing to better fine detail and colour accuracy

What actually happens after creation:

  1. The KSampler receives the empty latent and immediately populates it with random Gaussian noise using the seed value. The "empty" tensor is essentially discarded — the seed-noise is the true starting point.
  2. The diffusion model denoises this noise for N steps, guided by the text conditioning from the text encoder.
  3. The final clean latent exits the KSampler and goes to VAE Decode → pixel image.
In img2img workflows the Empty Latent Image node is not used — the input image is VAE-encoded into a real latent, partially noised, and fed directly to the KSampler. The Empty Latent Image node is exclusively a txt2img starting point. The Width and Height fields are the only place in a standard txt2img workflow where you set output resolution — they must respect the model's resolution constraints (see Section 0c).

3. Precision & Quantisation

How weights are stored and computed. Image DiT models tolerate quantisation better than UNet models (no conv2d layers), but are more sensitive than LLMs. Prefer Q5_K_M or higher for image quality.

Format Bit-width Notes for Image Models Quality Typical VRAM Impact
BF16 16-bit brain float Standard for all modern DiT image models (Flux, Qwen-Image, Z-Image). Most numerically stable FP16 variant. Best quality Needs full VRAM: ~16 GB (12B), ~40 GB (20B)
FP16 16-bit float Older GPU standard (pre-Ampere). Functionally equivalent to BF16 for inference. Slightly less stable in training. Excellent Same VRAM as BF16
FP8 8-bit float (E4M3/E5M2) H100/A100 native format. Near-BF16 quality at half memory. Recommended for Qwen-Image-2512 and Flux.2 Dev on 24 GB GPUs. Very good ~20 GB for Qwen-Image-2512
Q8 / INT8 (GGUF) 8-bit integer Near-lossless for DiT models. Best GGUF option when VRAM allows. Qwen Q8 GGUF runs on 16 GB 4060 Ti. Near-lossless ~21 GB for Qwen-Image-2512
Q6_K (GGUF) ~6-bit Excellent quality. Negligible perceptual difference from Q8. Recommended if Q8 is too large. Near-lossless ~16 GB for 12B model
Q5_K_M (GGUF) ~5-bit Good balance for mid-range GPUs. Recommended floor for image models (more sensitive than LLMs). Good ~12 GB for 12B model
Q4_K_M (GGUF) ~4-bit Most popular local format. Noticeable softening in fine texture/detail on image models. Widely used for Flux. Acceptable ~8–9 GB for 12B model
NF4 4-bit normalfloat (bitsandbytes) Used in HuggingFace BNB quantisation. Marginally better than INT4 at same width. Acceptable Similar to Q4
NVF4 NVIDIA 4-bit float (Nunchaku) RTX 50-series (Blackwell) specific. TensorRT-optimised. Very fast on 5090/5080. Good (Blackwell) RTX 5090/5080 only
Q3 / Q2 (GGUF) ~3–2-bit Heavy quality loss on image models. Only use as absolute last resort on very limited hardware. Poor Minimum VRAM but visible artefacts
Rule of thumb: GGUF file size in GB ≈ VRAM required. Q8 Qwen-Image-2512 (21 GB) runs on a 16 GB 4060 Ti with some CPU offloading.

4. Architecture Types

The underlying model design determines capability ceiling, ecosystem compatibility, and which quantisation formats work.

Architecture Used In How It Works / Key Trait Examples
UNet SDXL, SD1.5, SD2.x Encoder-decoder with skip connections. Mature, massive community fine-tune ecosystem. Conv2d layers make GGUF quantisation impractical — use FP16/BF16 safetensors. sdxl_base_1.0.safetensors
DiT
(Diffusion Transformer)		 Flux.1/2, SD3, Qwen-Image, Z-Image Pure transformer architecture replacing UNet. Scales better with parameters, superior text following, more robust to quantisation. No skip connections. All Flux models, SD3
Flow Matching Flux family, SD3 Training/sampling method: learns direct flow paths from noise to image rather than iterative DDPM noise removal. Enables fewer inference steps. Flux.1, Flux.2, Flux.1 Kontext
S3-DiT
(Single-Stream DiT)		 Z-Image, Z-Image Turbo Text and image tokens processed as one unified sequence (not dual-stream like Flux). Enables smaller, faster models without separate cross-attention branches. Z-Image, Z-Image Turbo
LLM Text Encoder Flux.2, Z-Image, Qwen-Image Uses a large language model as text encoder instead of CLIP/T5. Flux.2: Mistral-3 24B. Z-Image: Qwen3-4B. Qwen-Image: Qwen-VL. Massive improvement in complex prompt understanding. Flux.2 Dev/Klein, Z-Image, Qwen-Image-2512
VAE
(Variational Autoencoder)		 All models Compresses pixel images to/from latent space. Separate swappable component. Quality affects colour accuracy, sharpness, and fine detail. Each model family has its own VAE. ae.safetensors (Flux.1), flux2-vae.safetensors
ControlNet SDXL, Flux (via adapters) Add-on model that conditions generation on depth maps, edge maps, pose skeletons, etc. Must match base model architecture. controlnet-depth-sdxl.safetensors

7. Prompt Craft by Model

The text encoder determines what kind of language the model understands. Using SDXL-style keyword prompts on Flux produces mediocre results, and vice versa. Each model family has a distinct prompt dialect tied to its encoder architecture.

Keywords vs. Natural Language

Encoder Type Prompt Style Why
CLIP (SDXL) Short comma-separated keywords + quality tags 77-token hard limit. CLIP was trained on image captions, not prose. Understands visual keywords and style tokens better than grammar or relationships.
T5-XXL (Flux.1) Full sentences, descriptive prose 512-token limit. T5 is a sequence-to-sequence language model that understands grammar, relationships, and negation. Long structured descriptions work properly.
Mistral-3 24B (Flux.2) Complex multi-clause prose, narrative descriptions 32,000-token limit. A full LLM. Understands conditional statements, spatial relationships, story context, and nuanced instructions.
Qwen3-4B (Z-Image) Natural language sentences, bilingual capable LLM encoder. Handles long prompts well. Chinese and English both work natively without translation.
Qwen-VL (Qwen-Image) Natural language with very precise literal adherence Vision-language model encoder. Follows prompts almost too literally — vague prompts produce mediocre results, precise prompts produce exceptional ones.

Per-Model Prompt Reference

Model Negative Prompt? Length Sweet Spot Style Guide Example Prompt
SDXL 1.0 Yes — important for quality 50–150 tokens (short) Comma-separated visual keywords. Quality boosters ("best quality", "masterpiece") are trained into SDXL checkpoints and meaningfully improve output. Style modifiers ("cinematic", "oil painting") work well. Avoid sentences with verbs — CLIP doesn't parse grammar reliably. masterpiece, best quality, photorealistic portrait of a woman with auburn hair, cinematic lighting, shallow depth of field, sharp focus, 8K, artstation
Flux.1 [dev] No — guidance baked in 100–300 tokens (medium) Write as if describing a scene to a cinematographer. Full sentences with descriptive adjectives. Specify lighting, mood, and composition in plain English. Quality tags ("masterpiece", "8K") do nothing — they have no special meaning in T5. A woman in her mid-thirties sits by a rain-streaked window in a Parisian café. Soft afternoon light filters through the condensation on the glass, casting diffuse shadows across her open notebook. Film grain, 35mm.
Flux.1 [schnell] No 50–150 tokens (concise) Same natural language style as Flux.1 dev, but shorter prompts work better due to fewer steps. Schnell has less capacity to resolve complex scene descriptions in 1–4 steps. A neon-lit Tokyo street at 3am, rain-soaked pavement reflecting purple and pink signs, a lone cyclist in a yellow raincoat.
Flux.2 [dev/klein] No 200–1000+ tokens (go long) Use the full power of an LLM encoder. Multi-clause descriptions, conditional statements, spatial relationships, and narrative context all parse correctly. Writing a paragraph-length prompt genuinely improves output. A Victorian-era scientist's study, late 19th century. Three gaslights illuminate mahogany shelves lined with brass instruments and leather volumes. On the central desk, a half-dissected mechanical automaton rests beside an open journal with hand-drawn anatomical sketches. Candlelight catches the gears. Muted greens and ambers. Photorealistic, 8K detail.
Flux.1 Kontext [dev] No 50–200 tokens (edit-focused) Prompts describe the edit to perform, not the full scene. Be specific about what changes and what stays the same. Reference elements from the input image explicitly. Change the jacket to a red leather motorcycle jacket, keeping the person's face and pose identical. Background unchanged.
Z-Image Turbo No 100–400 tokens Natural language sentences. Qwen3-4B handles complex descriptions well. Chinese prompts work natively — no translation needed. An elderly Japanese carpenter in his workshop, surrounded by wood shavings and hand tools hanging in perfect order. Warm window light. Photorealistic, detailed skin texture.
Qwen-Image-2512 Optional 150–500 tokens Greatest strength and trap: follows prompts almost literally. Vague prompts produce average results; highly detailed prompts produce exceptional ones. Best-in-class for bilingual text rendering — specify Chinese characters in the prompt and they render correctly. A glass of iced coffee on a white marble table, top-down view. Ice cubes partially melted. Thin condensation on the glass. Next to it, a small vase with two white flowers and a leather-bound notebook open to a blank page. Natural light from the left. Studio photography style.

Universal Prompt Principles

Principle Explanation
Lighting first Specifying light source, quality, and direction is one of the highest-leverage additions to any prompt. "Soft window light from the left", "golden hour backlight", "neon sign reflections" dramatically affect output across every model.
Camera / lens language Focal length, aperture, and perspective terms work across all modern models. "35mm lens", "shallow depth of field", "wide angle distortion", "macro close-up" are understood because these terms appear pervasively in training data captions.
Avoid SDXL quality tags on DiT models For Flux and Qwen models, tags like "masterpiece", "best quality", "highly detailed", "artstation" are noise, not signal. These tokens carry no special meaning in T5, Mistral-3, or Qwen encoders — they are SDXL-era CLIP vocabulary.
Negative prompts: SDXL only Negative prompts work on SDXL via CFG. They do nothing on Flux, Z-Image, or Qwen-Image models because guidance is distilled into the weights — there is no unconditional pass for CFG to push against. For SDXL, a standard negative ("blurry, low quality, watermark, deformed hands") meaningfully improves output.
Composition language Explicit composition instructions work well on modern DiT models. "Rule of thirds", "subject in the lower left", "negative space in the upper right", "symmetrical composition" are all correctly parsed by T5/LLM encoders.
Iterative refinement Start with a concise core prompt, generate, then add detail to weak areas. Adding 20 words of specificity to a detail that came out wrong is more effective than writing a 400-word prompt from scratch.
Token limits are maximums, not targets. Flux.1 dev produces excellent results at 100–150 tokens for most scenes. The advantage of Mistral-3 in Flux.2 is not that you need to write 32K tokens — it's that when your scene genuinely requires complex relational descriptions, the model can resolve them correctly rather than mangling the grammar.
