0a. Core Pipeline Components

The six nodes every workflow contains — what they do, how they connect, and the most common mistakes at each stage.

Signal chain: text → Text Encoder → conditioning embedding → KSampler feeds this plus random noise into the Diffusion Model (N times per the Scheduler) → clean latent → VAE Decode → pixel image.

Text Encoder — CLIP / T5 / LLM

Converts your text prompt into a numerical representation (embedding) the model can work with.

How it worksOlder models (SDXL) use CLIP — short prompts, keyword-based. Modern models use T5-XXL or full LLMs (Mistral-3, Qwen3). LLM encoders understand grammar, relationships, and long complex sentences far better.
Files by modelSDXL: CLIP-L + CLIP-G  ·  Flux.1: CLIP-L + T5-XXL  ·  Flux.2: Mistral-3 24B  ·  Z-Image: Qwen3-4B  ·  Qwen-Image: Qwen-VL
Common mistakeLoading the wrong encoder for your model. T5 is the reason Flux handles long descriptive prompts much better than SDXL. Loads separately via DualCLIPLoader / CLIPLoader.

Diffusion Model — UNet / DiT

The core image generation engine — takes the text embedding plus a noisy latent and iteratively removes noise to produce your image.

How it worksThe main model file (12B or 20B parameters). Does NOT work on pixels — it works entirely in compressed latent space. Does not understand text itself; the text encoder hands it a pre-digested embedding.
ArchitectureSDXL: UNet  ·  Flux / SD3 / Qwen / Z-Image: DiT. Architecture determines everything downstream — scheduler choice, LoRA compatibility, VAE pairing.
ComfyUI node"Load Checkpoint" for SDXL (all-in-one). "Load Diffusion Model" for Flux, Qwen, Z-Image (diffusion model only — encoders and VAE are separate files).

VAE — Variational Autoencoder

Compresses full-resolution images into a smaller latent representation for the diffusion model to work in — and decompresses them back to pixels at the end.

How it worksWithout a VAE, the diffusion model would need to work at full pixel resolution, which is prohibitively expensive. The VAE is a lossy compressor: it trades some information for massive speed and memory savings. VAE quality directly affects colour accuracy, sharpness, and fine detail.
Files by modelFlux.1: ae.safetensors  ·  Flux.2: flux2-vae.safetensors  ·  SDXL: sdxl-vae-fp16-fix.safetensors  ·  Qwen-Image: its own separate VAE
Critical ruleVAEs are NOT interchangeable between model families. Modern models (Flux.2, Z-Image) use a 16-channel VAE vs the 4-channel VAE of SDXL — swapping them produces washed-out or distorted images immediately. Place all VAE files in models/vae/.

Scheduler — Sampler Schedule

Controls how noise is added and removed across the diffusion steps — the mathematical trajectory from pure noise to clean image. Not a neural network; it's an algorithm.

How it worksDifferent schedulers produce different results at the same step count. Flow Matching models (Flux) use straight-line probability-space trajectories — fundamentally different math from DDPM. This is why DDPM schedulers (DPM++, Karras, DDIM) cannot be freely swapped onto Flux.
Common schedulersDPM++ 2M Karras (SDXL quality, ~20 steps)  ·  Euler / Euler a (SDXL fast)  ·  Simple / SGM Uniform (Flux)  ·  DPM++ 3S (Qwen-Image fast, ~10 steps)
Common mistakeUsing DPM++ Karras or DDIM on a Flux model. Use Simple or SGM Uniform for Flux. Set inside the KSampler or SamplerCustomAdvanced node.

KSampler — The Sampler Node

The node that runs the denoising loop — calls the diffusion model N times, guided by the text embedding and scheduler, to produce the final clean latent.

How it worksAt each step, it asks the diffusion model "given this noisy latent and this prompt, what noise is here?" then uses the scheduler to take one denoising step. Also applies CFG: runs the model twice per step (conditioned + unconditional) and extrapolates toward the prompt. Flux models bake guidance in via distillation — CFG=1, one pass per step.
Key settingsSteps: 20–50 (standard), 4–8 (distilled)  ·  CFG Scale: 7–9 (SDXL), 1.0 (Flux schnell), 3.5 (Flux dev)  ·  Denoise: 1.0 = txt2img, <1.0 = img2img
NotesFor Flux, use the FluxGuidance node instead of standard CFG. SamplerCustomAdvanced gives more control than basic KSampler. Seed controls the initial noise pattern.

CLIP Text Encode — Prompt Node

Feeds your text prompt through the loaded text encoder and produces the conditioning embedding that guides the denoising process.

How it worksUsually two nodes — one for positive prompt (what you want) and one for negative prompt (what you don't). Flux models use no negative prompt: guidance is baked into the weights via distillation, so there is no unconditional pass for CFG to push against.
By modelSDXL: two CLIP Text Encode nodes (positive + negative)  ·  Flux.1/2: one CLIPTextEncodeFlux node with guidance parameter  ·  Qwen-Image: one text encode node, negative optional

VAE Decode — Output Node

Takes the final clean latent from the KSampler and runs it through the VAE decoder to convert it back into a full-resolution pixel image.

VariantsStandard VAE Decode for normal use. VAE Decode (Tiled) for very large images to avoid VRAM spikes during decoding. Latent upscale workflows: decode → upscale → re-encode → decode again.
Common mistakeIf output images look washed out, too saturated, or soft, the first thing to check is whether you loaded the correct VAE. The fp16-fix VAE for SDXL is critical — the original baked VAE in many SDXL checkpoints produces washed colours.
